**Студент:** Лагода Дмитро, ІПЗ-23-5

## 0. План рішення

| Поле | Значення |
|---|---|
| Проблема | До кожної лабораторної роботи (5+ дисциплін, кілька робіт на тиждень) потрібен звіт у форматі, який встановив викладач. Формати різні: «Розробка мобільних додатків» (РМД) — `README.md` з описом, структурою маршрутів, скріншотами і відповідями на контрольні запитання; «Моделювання та аналіз ПЗ» (МАПЗ) — `labNN_report.md` без зображень, з кодом PlantUML, що дослівно збігається з файлом `.puml`; «Програмування для ОС Linux» — документ Word з титульною частиною, покроковим ходом роботи і пронумерованими рисунками. Зміст звіту здебільшого вже є в коді та завданні. |
| Поточний процес | Звіт формується через чат з LLM: опис формату дисципліни, передача завдання, коду і скріншотів, вичитка результату, ручна перевірка оформлення, збереження. 6 ручних операцій, ≈20 хв на звіт. |
| Дані | Завдання (PDF або Markdown), тека проєкту (код, конфігурація, `.puml`), скріншоти. Усі дані локальні. |
| Рівень рішення | 3 — AI-агент. Перелік файлів, які треба прочитати, залежить від проєкту і стає відомим лише після перегляду структури; звіт доводиться до вимог кількома ітераціями «генерація → перевірка → виправлення». |
| Метрика + ціль | Час на один звіт: 20 хв → ≤ 5 хв. Кількість ручних операцій: 6 → ≤ 3. |
| Ризики / fallback | Вигадані факти — автоматична перевірка повноти прочитаних даних і обов'язкова вичитка перед збереженням. Недоступність API — повторні запити, резервні моделі, автозбереження чернетки. Детально — п. 4. |

## 1. Архітектура

```
Користувач ── чат у терміналі (/save /show /diff /undo /stats /quit)
     │
labreport.py ── профіль дисципліни (profiles/mobile.md, mmdo.md, linux.md):
     │          структура звіту, вимоги до стилю, параметри перевірок
     ▼
Gemini API (function calling, ручний цикл обробки викликів)
     │  list_dir, read_file, read_pdf, view_image   — лише читання, лише в межах дозволеної теки
     │  write_report, edit_report                    — звіт зберігається в пам'яті; запис на диск — командою /save
     │  check_report                                 — детермінована перевірка без участі моделі
     ▼
Звіт (README.md / labNN_report.md / .md + .docx), журнал сесії logs/*.jsonl, чернетка logs/*.draft.md
```

Для дисциплін, де звіт здається у Word (`export: docx` у профілі), модуль `md2docx.py` при `/save` конвертує Markdown у `.docx`: титульна частина, заголовки, абзаци за шириною, таблиці, код шрифтом Consolas, скріншоти з автоматичною нумерацією «Рисунок N — підпис».

Функція `check_report` перевіряє:
- наявність обов'язкових розділів, відсутність порожніх розділів і битих посилань;
- вставлення у звіт усіх скріншотів з теки `screenshots/`;
- **повноту вихідних даних:** агент прочитав усі файли коду, переглянув усі скріншоти та обов'язкові файли профілю (`glossary.md` для МАПЗ), причому до останнього запису звіту — інакше має переписати звіт;
- для МАПЗ — дослівний збіг блоків PlantUML з файлами `.puml` і відсутність зображень.

Якщо модель завершує роботу, а перевірка виявила порушення, скрипт повертає їй перелік зауважень (до двох разів).

## 3. Обґрунтування рівня рішення

| Варіант | Оцінка |
|---|---|
| Рівень 1: чат з LLM (поточний процес) | формат дисципліни і вихідні дані щоразу передаються вручну; оформлення перевіряється вручну |
| Рівень 2: скрипт об'єднує файли проєкту в один запит | проєкт містить сотні службових файлів (`node_modules`), набір значущих файлів різний для кожної роботи; відсутні самоперевірка і внесення правок |
| **Рівень 3: агент з інструментами** | самостійний вибір файлів, перевірка результату кодом, правки в діалозі |
| Рівень 4: fine-tuning | обсяг прикладів (≈10 звітів) недостатній; формат задається профілем без донавчання |
| Локальна модель `gemma3:4b` (ЛР 4) | обмеження 6 GB VRAM, слабка підтримка виклику інструментів і аналізу зображень |
| Платні Gemini API / Claude API | вища якість і відсутність лімітів, але потребують передоплати від $5; для задачі достатньо безкоштовного тарифу |

## 7. Аналіз результату

1. **Яку проблему вирішували?** Формування звітів до лабораторних робіт за різними вимогами дисциплін.
2. **Чому проблема реальна?** Звіт потрібен до кожної роботи; щоразу повторюються ті самі операції: опис формату, передача даних, перевірка оформлення.
3. **Як задача виконувалась до AI-рішення?** Через чат з LLM з ручною передачею коду і скріншотів та ручною перевіркою оформлення, ≈20 хв на звіт.
4. **Яке рішення побудовано?** CLI-агент на Gemini API з інструментами читання проєкту, профілями трьох дисциплін, детермінованою перевіркою, внесенням правок у діалозі та експортом у Word.
5. **Чому обрано рівень 3?** Набір вихідних файлів визначається під час роботи, а результат доводиться кількома кроками з перевіркою. Рівнів 1–2 недостатньо, для рівня 4 бракує даних.
6. **Які альтернативи розглядались?** Чат з LLM, об'єднання проєкту в один запит, локальна `gemma3:4b`, платні Gemini API і Claude API.
7. **Які моделі та інструменти використано?** `gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`, `gemini-3.6-flash`; `google-genai`, `pypdf`, `python-docx`, `rich`.
8. **Які проблеми виникли?**
   - Модель ігнорувала інструкції і вигадувала факти — додано перевірку повноти прочитаних даних.
   - Модель ігнорувала зауваження перевірки — додано автоматичне повернення.
   - Безкоштовний тариф: помилки 503/429, добовий ліміт 20 запитів — резервні моделі, пакетне читання файлів (19 викликів → 6).
   - Технічні помилки: таймаут HTTP-клієнта SDK не перехоплювався; сервер не приймав параметр `media_resolution` у відповіді інструмента; чернетка втрачалась при збої — додано автозбереження; помилка в перевірці порожніх розділів.
   - Модель викликала неіснуючий інструмент (`read_files`) — помилка повертається моделі текстом, сесія продовжується.
9. **Наскільки рішення надійне?** Оформлення стабільне, оскільки контролюється кодом. Зміст містить 2–3 фактичні помилки на звіт, тому вичитка обов'язкова. Для МАПЗ lite-модель формує поверхневий зміст. Безкоштовний тариф нестабільний.
10. **Що змінилося?** Формат дисципліни і вихідні дані більше не передаються вручну; оформлення перевіряється автоматично; ручна робота зведена до вичитки і правок.
11. **Скільки заощаджено?** ≈17 хв на звіт (20 → 3, ≈85%); при 3–4 звітах на тиждень — ≈1 год на тиждень. Вартість — $0.
12. **Що змінити в подальшому?** Профіль для бездротових мереж; оформлення Word за методичними вимогами; сильніша модель для МАПЗ; режим підготовки до захисту — генерація запитань за кодом роботи.
