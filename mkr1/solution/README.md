# labreport

CLI-агент для формування звіту до лабораторної роботи за вимогами дисципліни з внесенням правок у діалозі.

## Встановлення

1. Python 3.11+.
2. Залежності (з теки `solution`):
   ```
   pip install -r requirements.txt
   ```
3. Ключ Gemini API (безкоштовний тариф, картка не потрібна):
   - https://aistudio.google.com → **Get API key** → **Create API key**;
   - скопіювати `.env.example` у `.env` у теці `solution`:
     ```
     copy .env.example .env
     ```
   - відкрити `.env` і вставити ключ після `=`:
     ```
     GEMINI_API_KEY=ваш_ключ
     ```
   Файл `.env` є в `.gitignore` і в репозиторій не потрапляє. Замість файлу можна задати змінну середовища `GEMINI_API_KEY`.

Без ключа програма завершується з підказкою, де його взяти.

## Запуск

```
python labreport.py <тека_роботи> --profile <профіль> [--task <файл_завдання>]
```

Приклад — звіт до ЛР 4 з розробки мобільних додатків, завдання лежить окремим PDF:

```
python labreport.py D:\labs\mobile\lab4 --profile mobile --task "D:\labs\mobile\Лабораторна робота №4.pdf"
```

Агент читає завдання, код і скріншоти, формує чернетку і виводить diff. Далі — діалог:

| Команда | Дія |
|---|---|
| довільний текст | правка звіту («скороти висновок», «зміни підпис скріншота 3») |
| `/save` | записати звіт у файл |
| `/show` | показати звіт |
| `/diff` | різниця з файлом на диску |
| `/undo` | скасувати останню відповідь агента |
| `/stats` | кількість токенів і тривалість сесії |
| `/quit` | завершити роботу |

| Параметр | Призначення |
|---|---|
| `--profile` | профіль дисципліни `profiles/<name>.md` (`mobile`, `mmdo`, `linux`) |
| `--task` | файл завдання, якщо він поза текою роботи |
| `--out` | ім'я файлу звіту (за замовчуванням — з профілю) |
| `--hide` | файли, недоступні агенту (наприклад, наявний звіт для порівняння) |
| `--model` | модель Gemini (за замовчуванням `gemini-3.5-flash-lite`; резервні `gemini-3.1-flash-lite`, `gemini-3.6-flash`) |
| `--auto` | сформувати і зберегти звіт без діалогу |

## Профілі

`profiles/<name>.md`: метадані, далі вимоги до звіту текстом (передаються моделі як інструкція).

Формат результату задає профіль дисципліни, а не модель:

| Профіль | Дисципліна | Результат |
|---|---|---|
| `mobile` | Розробка мобільних додатків | `README.md` зі скріншотами |
| `mmdo` | Моделювання та аналіз ПЗ | `labNN_report.md`, без зображень, PlantUML дослівно з `.puml` |
| `linux` | Програмування для ОС Linux | `.md` + `.docx` (`export: docx`): титульна частина, рисунки з підписами |

Агент завжди пише Markdown. Якщо в профілі `export: docx`, при `/save` модуль `md2docx.py` додатково створює Word-файл з тим самим ім'ям.

| Ключ | Призначення |
|---|---|
| `output` | ім'я файлу звіту; `{n}` / `{nn}` замінюються номером роботи з назви теки (5 / 05) |
| `export` | `docx` — при `/save` додатково створюється Word-файл |
| `images` | `allowed` / `forbidden` |
| `screenshots` | тека скріншотів, які мають бути переглянуті та вставлені |
| `code` | тека коду, яку агент має прочитати повністю |
| `required` | обов'язкові фрагменти звіту через `;` |
| `puml_sync` | `yes` — блоки PlantUML мають дослівно збігатися з `.puml` |
| `read_root` | тека, в межах якої дозволено читання (`..` — тека дисципліни) |
| `must_read` | файли, обов'язкові до прочитання, через `;` |

## Принцип роботи

Gemini API з викликом інструментів: `list_dir`, `read_file`, `read_pdf`, `view_image` (лише читання в межах дозволеної теки), `write_report`, `edit_report`, `check_report`. Звіт зберігається в пам'яті, запис на диск — тільки командою `/save`; чернетка автоматично зберігається в `logs/*.draft.md`. `check_report` перевіряє звіт кодом, без участі моделі; якщо перевірка не пройдена, агент не може завершити роботу (до двох повернень). Журнал кожної сесії — `logs/*.jsonl`.
